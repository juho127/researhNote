# 연구노트 활용 지침

연구노트는 연구실 논문 프로젝트의 **날짜별 진행 기록**과 **논문 흐름(단계)별 누적 정리**를 팀과 공유하는 시스템이다.
이 스킬은 AI 도구(Claude Code 등)가 MCP 서버 `research-note` 의 도구로 연구자의 진행을 대신 기록하고 조회하는 방법을 정의한다.

## 데이터 구조 (한눈에)

| 개념 | 설명 |
|---|---|
| 카테고리 | 연구 그룹/팀. 같은 카테고리 구성원은 서로의 프로젝트를 보고 코멘트·검토한다 |
| 프로젝트 | 논문 하나. 현재 단계(stage)·상태(active/paused/done)·목표 학회·마감 |
| 단계 (stage) | `planning` 기획 → `literature` 리서치 → `method` 관련기법 → `experiment` 실험결과 → `writing` 논문작성 → `review` 검토·투고 |
| 단계별 정리 | 각 단계의 **누적 결론** (마크다운). 논문 해당 절의 뼈대. `update_stage` 로 갱신 |
| 기록 (entry) | **날짜별** 진행 로그. `log_progress` 로 추가. 팀원이 코멘트·검토 |
| 할 일 (task) | 다음 할 일. `add_task` / `update_task` |
| 검토 | 기록에 `requested` → 리드가 `approved` / `changes_requested` |

## 언제 기록하는가

- 실험 한 차례가 끝났을 때 (설정·수치·결론)
- 문헌 5편 이상 정리했거나 관련 연구 지형이 바뀌었을 때
- 방법론/모델 설계를 결정·변경했을 때
- 초고의 절 하나를 썼거나 그림·표를 만들었을 때
- 막혀서 팀의 의견이 필요할 때 (검토 요청)
- 사용자가 "기록해", "남겨", "정리해" 라고 했을 때 (항상)

세션 중 의미 있는 결과가 나왔는데 사용자가 기록을 언급하지 않았다면, 세션이 끝나기 전에 **"연구노트에 기록할까요?"** 라고 한 번 제안한다. 사용자가 거절하면 강요하지 않는다.

## 기록 절차

1. `whoami` 로 사용자·소속·프로젝트를 확인한다. 프로젝트가 여러 개면 대화 맥락으로 고르되 애매하면 묻는다. **새 연구를 시작한다고 명시했을 때만** `create_project`.
2. `get_project` 로 현재 단계·단계별 정리·최근 기록을 읽어 중복 기록을 피하고 맥락을 맞춘다.
3. `log_progress` 호출. 본문 마크다운 구성:

```markdown
## 한 일
- (구체적으로: 데이터셋, 모델, 설정, 실행 명령/노트북 이름)

## 결과
- (수치는 표로. 비교 대상·기준선 명시. 실패도 기록)

| 모델 | Acc | F1 | 비고 |
|---|---|---|---|

## 다음 할 일
- [ ] ...

## 메모
- (막힌 점, 가설, 팀에 묻고 싶은 것)
```

   - `title` 은 결과가 드러나게 한 줄로: "ResNet-50 baseline, CIFAR-10 acc 91.2%" (좋음) / "실험" (나쁨)
   - `stage` 는 작업 성격으로 고른다. 실험 코드 작성은 `method`, 실행·결과 분석은 `experiment`.
   - `date` 는 실제 연구일. 어제 한 일을 오늘 기록하면 어제 날짜.
4. 누적 결론이 바뀌었으면 `update_stage` 로 해당 단계 정리를 갱신한다. **덮어쓰기**이므로 기존 정리를 읽고 병합한 전체 텍스트를 보낸다. 단계가 실질적으로 끝났으면 `status: done`, 다음 단계로 넘어가면 `set_current: true`.
5. "다음 할 일" 항목은 `add_task` 로 등록한다. 이미 있는 할 일이 끝났으면 `update_task status=done`.
6. 사용자가 검토를 원하면 `log_progress` 에 `request_review: true` 또는 `set_review`.

## 조회·검토

- 팀 찾기·가입: `list_teams`(전체 팀·가입 정책·내 상태) → 사용자가 원하면 `join_team`(즉시 가입 또는 리드 승인 요청). 한 사람이 여러 팀에 속할 수 있다.
- 팀 상황: `team_overview`(구성원·프로젝트·검토 대기), `team_feed`(최근 활동)
- 특정 기록 읽기: `list_entries` → `get_entry` (코멘트 포함)
- 팀원 기록에 의견: `add_comment`. 리드/관리자만 `kind: approve | request_changes`
- 보고서: `get_report` (마크다운). 주간 미팅 준비 시 `from`/`to` 로 기간 지정

## 작성 원칙

- 사용자의 언어(기본 한국어)로 쓴다. 코드·명령·경로는 백틱.
- **사용자가 실제로 한 일과 실제 결과만** 기록한다. 추정·희망을 사실처럼 쓰지 않는다. 불확실하면 "추정" 이라고 표시.
- 수치는 소수점 자리·단위·시드·반복 수를 함께 적는다.
- 실패한 실험도 기록한다 (원인 가설 포함). negative result 는 가치가 있다.
- 한 기록에 한 주제. 서로 다른 작업은 기록을 나눈다.
- 개인정보·비밀키·미공개 데이터 원본은 기록하지 않는다.

## 오류 처리

- `unauthorized` → 토큰이 없거나 회수됨. 사용자에게 관리자로부터 새 토큰을 받아 MCP 설정을 갱신하라고 안내.
- `forbidden` → 권한 부족(다른 사람 프로젝트에 기록 시도 등). 소유자에게 코멘트로 남기거나 자신의 프로젝트에 기록.
- `not_found` → ID 오타. `whoami`/`list_projects` 로 다시 확인.
